## 阻塞诊断与修复建议（未实施）

Avalonia 的实际组合不是“外层 Dispatch 自动保证所有生命周期”：仓库 AvaloniaTestLifecycleTests 的初始化为同步方法，异步清理主体显式 Dispatcher.UIThread.InvokeAsync；测试方法 await 则使用 UI 上下文。HeadlessUnitTestSession 提供队列、应用同步上下文与 DispatcherFrame 消息泵；AvaloniaTestClassAttribute 尾部 TaskScheduler.Default continuation 用于避免在 Headless 线程内清理并等待自身，不是修复 MSTest 内部线程漂移。不能用其历史 543 个离线通过结果证明 WPF 当前更强的异步生命周期契约成立。公开 Headless master 源码仅作机制参考，本轮未取得精确 12.1.0 标签源码，不声称已审计对应二进制内部实现。

最小必要设计是**单一 WPF Application/Dispatcher 所有者 + 活跃消息泵 + 每段 UI 操作明确回到该 Dispatcher**，而不是再给 inner.ExecuteAsync 入口增加未经证实的调度包装。

优先候选：保持 4.0.2 和共享 WPF 宿主，保留真正 async 的初始化/清理，将各自完整 UI 主体显式投递并 await；UI/线程/上下文断言仍应在实际 UI 主体执行，测试使用同一入口，MSTest 仍正常管理实例、参数及生命周期，不反射手工调用、不跳过或删断言。**这改变了“原始生命周期入口全在共享 UI”的契约，必须先由用户批准；本轮不移动任何断言、不应用该方案。**

[MSTest 公开执行控制](https://learn.microsoft.com/dotnet/core/testing/unit-testing-mstest-writing-tests-controlling-execution)支持 Windows 上 STATestClass/STATestMethod（3.6+）；4.1 起 `STATestMethod(UseSTASynchronizationContext = true)` 可保留异步 STA continuation，默认 false。但它不是共享 WPF DispatcherSynchronizationContext、现有 Application 所属线程或完整生命周期的保证；UITestMethod 的官方用途是 UWP/WinUI。单纯升级 4.1.0 不能作为修复结论。参见 [testfx #5729](https://github.com/microsoft/testfx/issues/5729)。

若必须坚持“原始生命周期入口与 continuation 全在同一共享 WPF STA”，须先核验框架正式的整个生命周期/宿主集成支持，再决定框架版本/运行器和 Application 所有权。**用户需选择显式 UI 边界方案，或坚持强契约并选择受支持集成；任何版本、包范围或跨用例线程共享架构调整均不自动决定。**

解阻门槛：补原始失败日志，锁定设计后先验证一个含真实 await 的异步初始化→测试→异步清理闭环，记录每个边界的线程 ID、STA、SynchronizationContext、Dispatcher.CheckAccess 与顺序；再验证完整 14 项、双语言/参数、异常恢复、资源、真实输入、PNG 和退出/超时。阶段 2 通过前不开始阶段 3。详见[对齐计划](../../../Docs/WPF与Avalonia功能界面对齐计划.md)与[验收矩阵](../../../Docs/WPF与Avalonia功能界面验收矩阵.md)。
