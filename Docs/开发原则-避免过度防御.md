# 开发原则：避免过度防御

## 原则

过度防御有害：没有真实业务或底层契约依据的限制，会阻断合法用法，迫使调用方增加分支，并衍生额外 API、状态和测试。代码质量与可读性优先，不为假想风险增加机制。

添加校验之前，应确认被拒绝的输入为什么不合法、底层是否已经支持它，以及校验是否确实保护了必要的不变量。不能因为输入为空，就默认它是错误。

这不意味着删除所有校验。`null` 等契约错误与有明确语义的空集合应分别判断；保留必要校验，不扩展没有依据的限制。

## 本次教训：Chat 空输入继续

`CodingAgent.RunAsync` 曾拒绝空 `contents`。但底层支持零条新输入，直接使用现有 Session 历史继续运行。空集合不是空 User 消息，而是不添加 User 消息。

为了绕过这条限制而新增 `ContinueAsync`、已有 Session 校验和共享准备方法，是由过度防御衍生出的额外设计。不能再以这些刚新增的结构存在为理由，要求维护所谓兼容性。

正确实现：

- `RunAsync` 接受空集合；非空集合创建 User 消息，空集合传零条输入消息。
- 使用同一个 Session 和助手输出对象，即可继续历史并追加输出。
- Shell 的重试按钮复用这条执行路径，不在 AgentLib.Coding 另建继续 API。
- 测试验证空输入的合法行为、历史复用与输出追加，不固化无依据的拒绝规则。

## 修改边界

- 优先删除多余限制，复用已有能力，而不是为绕过限制增加新入口。
- 新增抽象必须来自真实差异；业务名称不同，不代表需要不同的底层执行机制。
- 不顺手修改无关业务规则，不为边缘情况增加防御层或恢复框架。
