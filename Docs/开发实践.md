# 开发实践

## 基本原则

1. 禁止过度设计，禁止过度防御。
2. 项目要长期维护，禁止补丁式实现；采用符合实际业务的最佳实践。代码质量、代码可读性第一。
3. 禁止分期，要求完整完成。不得把未完成、未验证或无法统一解释的部分推迟为“首期不做”“PoC 阶段”“后续扩展”。“首期不做”不等于“首期已做到”，这类表述本身不构成设计。

设计应基于真实需求和现有代码能力，不为假想场景添加抽象、限制或恢复机制。相关案例见[开发原则：避免过度防御](开发原则-避免过度防御.md)。

## 日志记录

- 日志字段名使用 `PascalCase`。
- 日志性能优先，减少对象分配。
- 直接记录原始配置值，不为日志额外解析或转换配置。
- 使用方括号标识模块或类名；可增加第二层，标识方法或动作，例如 `[CodingAgent][Run]`。

对于记录日志而言，记录的日志都需要反问自己，这个日志看了记录之后，能否定位出来问题的原因。如果不能，那这条日志就需要优化或者删除

## 异常处理

### 沿完整调用链明确处理责任

对每一处抛出的异常，都必须追踪完整调用链，确保由业务代码捕获并在业务中正确处理。

- 不得让异常传播到顶层导致进程崩溃，或把顶层兜底处理当作正常异常处理路径。
- 下层业务未捕获的异常，必须在上层业务中有补充捕获和处理逻辑，不得继续漏出业务边界。
- 捕获必须产生明确的业务处理结果；仅记录日志、静默吞掉异常，或转交全局兜底，不等于完成业务处理。
- 不要求每一层重复捕获；应在具有处理责任的业务层完成处理，避免没有业务含义的层层包装。

例如，调用链为 `A → B → C`，如果 C 抛出 `XxException`，则 A 或 B 必须存在对应业务捕获和处理逻辑。

如果 C 只有带过滤条件的捕获：

```csharp
catch (Exception exception) when (xxx)
{
    // 处理满足 xxx 的情况。
}
```

则 A 或 B 必须对不满足 `xxx`、继续向上传播的异常补充捕获，并正确完成业务处理，不能只考虑过滤条件成立的路径。

### 异常必须能够定位问题

每个抛出的异常都必须有助于定位问题。设计异常时必须回答：

> 如果只收到这个异常，能否准确定位问题发生在哪里？

如果不能回答，说明异常设计不正确，必须重新设计。异常类型、消息、必要上下文和异常链应足以说明失败操作及原因；不能通过丢失原异常或缺少上下文的泛化消息掩盖实际问题。

## 界面设计规范

### 风格与语言

- 使用 Windows 11 时代的 Fluent 界面风格与 Mica 背景。
- 界面应现代、有特色、简洁、养眼。
- 功能文案必须经过设计，表达准确、合理，默认使用简体中文。

### 功能组织与布局

- 功能组织、层级、操作分组及视觉分区必须合理。
- 信息密度适中，与 Windows 11 设置界面相当；尤其是设置界面，可考虑使用 Windows 11 设置中的设置卡片设计。
- 列表可能很长，每项应保持适度的单行高度：不能过高而降低信息密度，也不能过低而显得拥挤。
- 减少标题嵌标题、卡片套卡片的设计，避免无意义的层级和容器。

### 内容展示

界面显示的任何内容都必须经过设计，不得随意展示。必须充分考量信息的展示方式，包括内容是否必要、出现的位置、视觉层级、文案及与当前操作的关系。异常、状态、提示和操作结果同样适用。

不得将与开发者交流的对话在界面中展示出来。

## 文档/注释撰写守则

1. 撰写时注意目标读者
    - 代码注释的目标读者为代码维护人员
    - 文档的目标读者为代码维护人员，或产物用户
    - 不存在目标读者为智能体会话参与人的代码、注释或文档，而这也是 AI 撰写文档时最容易犯的错误
        - 如提到仅智能体会话上下文才存在的引用：`方案 A`、任务编号 `T8` `Q3`、章节编号 `§x.x`
        - 如使用智能体对话语气：`按你说的`、`给用户看的`
    - 文档和注释尽量使用正向描述（是什么，应该怎么），而非负向描述（不是什么，不应该怎么），因为 AI 写文档时的负向描述大多都是对凭空出现的离谱概念进行反驳，不具备参考价值
2. 文档/注释的撰写应遵循奥卡姆剃刀原则
    - 只写必须要写的内容，禁止长篇大论
    - 避免在各处澄清同一个描述，这会让此描述几乎无法修改和维护，应尽量集中在一处说明（在一些地方不提及这些描述看似存在歧义风险，实则整体文档/注释/代码已经具备确定性解释，同时还更利于修改和维护）
    - 避免注释间交叉引用和相互说明，这会导致注释难以修改；如需描述其他模块与自身的交互，尽量使其通用化或抽象化，避免特指某一个或某几个模块
    - 除导航地图类文档外，避免文档间相互引用（尤其避免网状文档引用），因为 AI 编写的文档经常强调无关紧要的细节导致很容易过时，进而导致随着引用网传递使所有文档过时
    
3. 文档信息密度要高，避免重复
    - 相同的知识点不应在多处、多份文档中重复出现。
    - 重要结论不应被大量枚举、模板、阶段说明和防御性描述所淹没。
    - 多份文档不应重复描述相同的背景、状态、风险、流程和边界。
    - 判断标准：篇幅增长是否带来了等比例的信息确定性？如果篇幅翻倍而确定性不变，应压缩和去重。

## 方案设计的约束

### 1. 控制复杂度，优先稳定性

- 设计方案不应引入过多的层次、状态、注册中心、协调器、生命周期阶段、租约、回退路径、功能开关和回滚策略。
- 如果设计实现出来会充满补丁式分支和防御性回退逻辑，说明设计本身需要简化。
- 以**可证明正确性**（而非"看起来覆盖了所有场景"）作为衡量标准。复杂度的增加必须带来等比例的确定性，否则应拒绝。

### 2. 用抽象而非枚举来证明完备性

- 不应以枚举具体实现来代替抽象。
- 枚举增长时，暴露的不是"覆盖全面"，而是"设计仍由具体场景和实现细节驱动"。
- 正确的抽象应当让新场景被**推导**出来，而非被**添加**进去。如果每次新增场景都需要修改核心模型，说明抽象点找错了。
